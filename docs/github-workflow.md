# GitHub workflow

Процесс рассчитан на небольшую команду и должен оставаться лёгким.

## Путь задачи

`Идея → Issue → В работе → Pull Request → Review → Готово`

## 1. Issue

Выберите шаблон: ошибка, улучшение или рабочая задача. Хорошая Issue отвечает на три вопроса:

1. Зачем это нужно?
2. Что должно измениться?
3. Как проверить готовность?

Приоритеты:

- `P0` — работа продукта заблокирована;
- `P1` — важно сделать в ближайшее время;
- `P2` — плановая работа;
- `P3` — улучшение без срочности.

## 2. Ветка

Создавайте ветку от актуальной `main`:

- `feature/42-registration` — новая возможность;
- `fix/57-sheets-timeout` — исправление;
- `docs/18-team-roles` — документация;
- `chore/31-update-dependencies` — обслуживание.

Число — номер Issue. Название короткое, на английском, через дефисы.

## 3. Коммиты

Коммит должен описывать результат: `feat: add member registration`, `fix: handle empty sheet row`, `docs: clarify designer workflow`.

## 4. Pull Request

- Заполните шаблон полностью.
- Свяжите PR с Issue через `Closes #42`.
- Приложите способ проверки.
- Для изменений пользовательского сценария добавьте скриншоты или примеры сообщений.
- Не смешивайте рефакторинг и новую функцию без необходимости.

## 5. Review и объединение

Минимум один владелец затронутой области проверяет изменение. Замечание либо исправляется, либо обсуждение завершается аргументированным решением. Предпочтительный способ объединения — **Squash and merge**.

Прямые изменения в `main` допустимы только для срочного восстановления продукта и всё равно должны быть описаны в Issue постфактум.

## Рекомендуемые настройки репозитория

После появления первого стабильного кода включить защиту `main`:

- Pull Request обязателен;
- минимум одно одобрение;
- обсуждения должны быть закрыты;
- проверки должны пройти;
- force push и удаление ветки запрещены.
